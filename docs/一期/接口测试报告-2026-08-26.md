# 一期现有接口测试报告（2026-08-26）

## 1. 验收结论

本轮对当前已注册的建筑、楼层、房间、分类共 20 个接口进行了实际 HTTP 请求验证，并结合代码和一期计划复查实现完整性。

结论：**部分通过，分类 CRUD 尚不能认定为完整，当前一期整体仍处于基础资料 CRUD 阶段。**

- 建筑、楼层、房间、分类均已具备 Create、Update、Delete、View、List 路由和调用链。
- 楼层和房间的 10 个接口本轮主流程测试通过。
- 建筑 5 个接口的主流程可用，但删除保护会被已软删除的楼层永久阻塞。
- 分类 5 个接口均已接通，不再存在空 Controller 或空 Logic；但 List 分页错误，Update 缺少关键校验，View 错误文案错误，Delete 缺少产品引用保护。
- 产品 CRUD、资产 CRUD、自动编码、入库、转移和位置记录尚未实现，因此一期业务闭环尚未形成。

## 3. 现有接口逐项结果

### 3.1 建筑接口

| 方法与路径 | 结果 | 说明 |
| --- | --- | --- |
| `POST /asset/building/create` | 通过 | 成功创建测试建筑 |
| `PUT /asset/building/update` | 通过 | 名称、地址、备注更新成功 |
| `GET /asset/building/view` | 通过 | 能按 ID 返回更新后的建筑 |
| `GET /asset/building/list` | 通过 | 编码筛选和列表返回正常 |
| `DELETE /asset/building/delete` | **部分通过** | 存在楼层时能阻止删除；楼层软删除后仍然阻止建筑删除，无法完成正常清理 |

删除异常的复现结果：先创建建筑、楼层和房间，再依次删除房间和楼层；此时删除建筑仍返回：

```json
{"code":500,"message":"建筑下存在楼层,无法删除","data":null}
```

代码原因是建筑删除调用的楼层查询使用了 `Unscoped()`，把已软删除楼层也视为有效引用。

### 3.4 分类接口

| 方法与路径 | 结果 | 说明 |
| --- | --- | --- |
| `POST /asset/category/create` | 通过 | 根分类和子分类创建成功 |
| `PUT /asset/category/update` | **部分通过** | 正常更新成功，但不存在 ID 也返回成功，且允许把自身设为父分类 |
| `GET /asset/category/view` | **部分通过** | 有效 ID 查询成功；不存在或已删除时错误文案为“建筑不存在” |
| `GET /asset/category/list` | **不通过** | `Page` 的页码和每页数量参数传反，标准分页会返回错误数据 |
| `DELETE /asset/category/delete` | **部分通过** | 子分类引用保护有效；缺少产品引用保护 |

分类分页的实测证据：

- 请求 `page=1&pageSize=20`，数据库中存在匹配记录且 `total=1`，但 `items=null`。
- 请求 `page=1&pageSize=1` 返回 1 条；请求 `page=2&pageSize=1` 反而返回 2 条。
- 当前代码为 `Page(req.PageSize, req.Page)`，其他资源均为 `Page(req.Page, req.PageSize)`。

分类更新的实测证据：

- 更新不存在的 ID `18446744073709551614` 返回 `code=0`。
- 把分类 ID 1 的 `parentId` 设置为 1 返回 `code=0`，与计划中“父分类不能选择自己”的要求不符。

分类详情不存在时返回：

```json
{"code":500,"message":"建筑不存在","data":null}
```

## 4. 发现的问题

| 优先级 | 问题 | 影响 | 建议修复 |
| --- | --- | --- | --- |
| P1 | 分类 List 的 `Page` 参数传反 | 分页结果丢失或数量异常 | 改为 `Page(req.Page, req.PageSize)` |
| P1 | 建筑删除把软删除楼层算作引用 | 删除过楼层的建筑永远不能删除 | 删除保护查询不要使用 `Unscoped()`，只统计有效楼层 |
| P1 | 分类 Update 不校验记录存在 | 不存在 ID 也返回成功，调用方无法判断结果 | 更新前查询有效分类，或检查更新影响行数 |
| P1 | 分类 Update 允许 `parentId == id` | 可形成自引用，破坏分类树 | 按计划增加自身父级校验；后续再确认是否禁止更深层循环 |
| P1 | 分类 Delete 缺少产品引用保护 | 产品实现后可能删除仍被引用的分类 | 删除前统计未删除产品引用 |
| P2 | 分类 View 的不存在文案错误 | 客户端和排障信息误导 | 改为“分类不存在” |
| P2 | 房间 List 返回 `Items` | 四类列表响应协议不一致 | 为字段增加 `json:"items"` |
| P2 | 业务错误仍返回 HTTP 200 | 监控和通用 HTTP 客户端难以按状态判断失败 | 确认全局错误响应规范；若保留应用码，应在接口文档中明确 |
| P2 | 创建接口不返回新 ID | 后续操作必须额外查询列表获取 ID | 统一确认 Create 响应是否返回 ID |
| P2 | 没有自动化测试 | 当前回归完全依赖人工请求 | 至少为 Logic 约束和 20 个路由增加集成测试 |

补充风险：分类编码查询没有使用 `Unscoped()`，而数据库唯一索引会保留软删除记录。分类软删除后再次创建相同编码，可能直接触发数据库唯一键错误，而不是业务层的可读提示；建筑、楼层、房间也需要统一确认“软删除后编码是否允许复用”。
