# 一期现有接口复测报告（2026-08-27）

## 1. 复测结论

本轮针对 2026-08-26 首轮接口测试报告中的问题重新检查当前工作区，并使用当前源码启动独立服务，对建筑、楼层、房间、分类共 20 个现有接口及关键失败场景执行数据库实测。

结论：**当前源码的 20 个接口主流程通过复测，33 个接口与约束断言全部通过；分类功能仍有产品引用保护和软删除编码复用问题，暂不认定为完全完成。**

- 建筑、楼层、房间、分类的 Create、Update、Delete、View、List 路由均可正常调用。

- 分类软删除后复用相同编码会返回原始 MySQL 唯一键错误。

## 6. 剩余问题与建议顺序

### P1：分类删除缺少产品引用保护

一期计划要求分类存在未删除产品时禁止删除。当前 `CategoryDelete` 只检查子分类，然后直接软删除分类。应在产品表可用的前提下增加有效产品计数，并补充对应失败场景验证。

### P1：明确软删除后的业务编码策略

当前分类编码查询只检查有效记录，但数据库唯一索引包含软删除记录。实测复用已软删除分类编码时，接口直接返回包含 SQL 的原始错误：

```text
Error 1062 (23000): Duplicate entry ... for key 'asset_category.uk_asset_category_code'
```

需要统一决定：

1. 编码永久不可复用：业务查询包含软删除记录，并返回“分类编码已存在”；或
2. 编码允许复用：调整数据库唯一索引与软删除设计。

建筑、楼层、房间和后续产品也应采用同一策略。

### P2：统一接口响应规范

- 确认业务失败是否继续使用 HTTP 200 加应用层错误码。
- 确认 Create 接口是否统一返回新记录 ID。
- 在产品开发前补充 Logic 或接口集成自动化测试，降低后续人工回归成本。

推荐处理顺序：

1. 补齐分类删除的产品引用保护。
2. 确认并统一软删除后的编码复用策略。
3. 重启 GoLand 中的 8000 服务，使用当前源码执行一次冒烟验证。
4. 形成分类功能提交后，再开始产品 CRUD。
